# 02 分析服务（`autocraft-analysis`）

实现 `ProjectService`、`AnalysisService`、`InboxService`（01-契约 §4.1–4.3），并提供分析通道的服务端（03 §2）。这是唯一能同时看到 craft-anything 的 `engine`、`mcp` 和 autocraft core 的 crate（`autocraft-rebuild` 也依赖 craft-anything，但只用 engine 层）。

## 1. 模块

| 模块 | 职责 |
|---|---|
| `lib.rs` | 公开入口：`AnalysisHub::new(config) -> Arc<AnalysisHub>`，以及三个 trait 的实现 |
| `engines.rs` | 每个项目一个 `Engine`：加载、引用计数、释放 |
| `session.rs` | 构造 `Session`：隔离目录、设置、项目、inbox、素材密钥 |
| `projects.rs`、`project_dto.rs` | `ProjectService`：列表、新建、重命名、复制、删除、用户字段；工作区到 core DTO 的转换和规范化项目 id |
| `view.rs` | `AnalysisView` 快照与缓存；非阻塞读 |
| `calls.rs` | `AnalysisService::call`：调用分析工具，处理执行确认、进度、取消、错误转换 |
| `catalog.rs` | 工具目录：`ToolInfo`、可用性、翻译 key；DSH 长工具判定 |
| `host_exec.rs`、`wire.rs` | 宿主执行表：等待类工具在 Engine 锁外执行（§10），以及与 MCP 一致的响应格式 |
| `inbox.rs` | `InboxService`：读写项目 inbox；监视新卡片 |
| `channel.rs` | 分析通道服务端：为每条管道连接起一个 `ca_mcp::serve` |
| `settings.rs` | `<data>/analysis/config.toml` 的读写（`AnalysisSettings`） |
| `install.rs` | 不依赖项目、经用户确认的外部引擎安装（`install_engines`） |
| `plugins.rs` | WASM 插件检查：每个检查能看到的复刻上下文 |
| `errors.rs` | `ToolError` → autocraft `Error` |

## 2. 引擎实例模型

**每个项目一个 `Arc<Engine>`。** 理由：

- craft-anything 的 `Session` 一次只持有一个 `Project`（调查记忆、账本）和一个 `InboxDir`，项目之间不能共用一个 session；
- 同一个项目里，界面、所有聊天的 Agent、复刻构建方必须看到同一份目标和证据，所以同一个项目必须共用一个 session。

```rust
struct Loaded {
    engine: Arc<ca_engine::Engine>,
    /// 引用者：活着的聊天（按 ChatId）、运行中的复刻、界面上打开的视图。
    holders: HashSet<Holder>,
    view: Mutex<AnalysisView>,  // 上一次成功读到的快照
}

enum Holder { Chat(ChatId), Run, View }

pub struct AnalysisHub {
    data_dir: PathBuf,
    loaded: parking_lot::Mutex<HashMap<ProjectId, Loaded>>,
    asset_keys: Arc<dyn AssetKeySource>,  // 从 autocraft.db 读 fal.ai 密钥（04 §5）
    inbox_tx: async_channel::Sender<InboxNotice>,
}
```

- `open(project)` 时如果还没加载，就构造 `Session`（§3），然后调用 `Engine::shared_with(session, extra, runtime)`：
  - `extra` 放 `autocraft-rebuild` 提供的 `rebuild_*` ToolSpec（05 §11）；
  - `runtime` 放分析配置中已启用的插件工具；Session 初始化后安装 WASM 插件。插件工具与普通工具共用净室 / 深度限制和执行确认，不另建工具通道。
- `close` 只有在 `holders` 为空时才真正释放 `Engine`。
- `hold(project, holder)` 和 `release(project, holder)` 是 crate 内接口，由聊天启动/关闭（03 §1）和复刻运行开始/结束（05 §2）调用。
- 应用退出时，按“取消所有进行中的调用 → 释放复刻 → 释放聊天 → 丢弃 Engine”的顺序关闭。

`loaded` 锁只保护这张表，**持有它的时候不调用 Engine**，以免和 Engine 的 session 锁形成锁序问题。

`AnalysisService::plugin_checks(project, kind)` 返回适用检查的 id、标题和正文扩展名；`run_plugin_checks` 在释放 session 锁后执行检查，保留通过状态、相似度、说明与取消。没有适用插件时，复刻检查不扫描额外文件。文件上下文会标记无法读取 / 非 UTF-8 / 超限的正文，不能以空正文伪装读取成功；缓存指纹包含当前检查集合。

## 3. Session 的构造

```rust
fn build_session(data_dir: &Path, ws: &Workspace, settings: &Settings, keys: AssetKeys) -> Result<Session> {
    let dir = data_dir.join("analysis");
    let mut s = Session::isolated(&dir);   // config_dir、engines.store_dir、projects_dir 都在 <data>/analysis 下
    s.settings = settings.clone();       // 从 <data>/analysis/config.toml 读出的全局设置
    s.settings.engines.store_dir = Some(data_dir.join("engines"));
    s.settings.ai = toml::Table::new();    // 模型配置不在这里（概要 §5.4）
    let project = Project::open(&ws.investigation_dir())
        .or_else(|_| Project::create(&ws.investigation_dir(), &ws.manifest.name, Purpose::default()))?;
    s.open_project(project)?;
    s.ext.insert(Arc::new(InboxDir(ws.inbox_dir())));
    s.ext.insert(Arc::new(keys));
    s.deep_for_run = Some(mode_of(ws) == AnalysisMode::Deep);
    Ok(s)
}
```

- 全局分析设置只有一份：`<data>/analysis/config.toml`，读写都用 craft-anything 的 `Settings::load_from` / `save_to`，保留它的版本迁移和“新版本只读”规则。
- 项目的分析模式不改全局 `deep_mode`，而是设置这个 Session 的 `deep_for_run`。模式按项目保存在 `autocraft.db` 的 `project_prefs` 表（04 §3）；新项目的默认值见 §6。
- `Session::isolated` 会把 `projects_dir` 设到 `<data>/analysis/projects`，之后再用 `ProjectLocations` 覆盖成真正的项目目录。

## 4. 项目注册（`ProjectService`）

- **列表**：`Workspace::list_in(&[default_dir, ..extra])`，然后转成 `ProjectSummary`。`pending_requests` 由 `Inbox::new(ws.inbox_dir()).pending().len()` 得到。
- **新建**：

  | `Door` | 调用 | 之后 |
  |---|---|---|
  | `MakeMyOwn` | `folder` 为空用 `Workspace::create(default_dir, name, request, target)`，否则用 `Workspace::create_at(folder, …, existing)` | 写入项目级模型选择；界面随后调用 `RebuildService::start` |
  | `WorkOnMine` | `Workspace::create_at(folder, name, request, TargetRef::None, existing)`，`app_in_root = true` | 同上 |
  | `LookInside` | `Workspace::create(default_dir, name, "", target)` | `AnalysisService::open`，再调用 `core_target_open` 和 `core_target_triage`，然后切到工作台 |

  `folder` 是用户选的目录时，调用 `Session::remember_project` 把它记进 `project_folders`。
- **重命名、复制、删除**：分别调用 `Workspace::rename`、`duplicate`、`delete`。删除前检查：没有运行中的复刻，`AnalysisHub` 里没有这个项目的持有者，否则返回 `BUSY`。
- **用户字段**：用 `Workspace::set_person(|m| …)` 修改 `approvals`、`questions`、`asset_budget_usd`、`generate_assets`。这个函数会先从磁盘重读用户字段再写回，保证构建过程中修改设置不会被运行中的保存覆盖。
- **只读项目**：`Workspace::is_read_only()` 为真时，所有写操作返回 `READ_ONLY`，界面只读显示。

## 5. 视图快照（`view`）

- `view()` 用 `engine.try_session()` 读取：
  - 拿到锁：读出目标、当前目标、证据账本最新 300 条、未知项，更新缓存，`revision` 加一，`stale = false`；
  - 拿不到锁：返回缓存，`stale = true`，`busy` 填当前正在运行的工具 id。
- **谁在运行**：Engine session 锁上的标签（`MutexGuard::label`）没有公开的读取接口，所以 autocraft 自己记：每个 `Loaded` 有一张“进行中的调用”表（工具 id、来源、开始时间）。界面调用在 `calls.rs` 里登记和注销；分析通道的调用由 `PolicyReader` 看到 `tools/call` 时登记、`ObservingWriter` 看到对应 id 的响应时注销。`busy()` 返回表里最早的一条，只读这张表，不碰 session 锁。
- 证据账本：`session.ledger()` 已经是新的在前（内存里最多 5000 条，其余留在磁盘按 id 解析），截取前 300 条。
- 界面拿到 `stale = true` 时显示“正在运行：<工具>”，并在 1.5 秒后重试。
- 什么时候刷新：
  - 界面发起的 `call` 完成后；
  - 分析通道里任意 `tools/call` 完成后（§9 的 `ObservingWriter`）；
  - 复刻的 `Checked` / `Finished` 事件之后。

  三者都发 `AnalysisChanged { project }` 给界面，界面再取一次 `view()`。

## 6. 净室与深度

- **新项目的默认值**：`LookInside` 默认 `Deep`；`MakeMyOwn`、`WorkOnMine` 默认 `CleanRoom`。Make 页可以改。
- **切换**：`set_mode(project, mode)` 依次：
  1. 写 `project_prefs.mode`；
  2. 在 session 上设置 `deep_for_run`；
  3. 发 `AnalysisChanged`；
  4. 通知 `autocraft-agents`：这个项目所有空闲会话标记“下次发送前重启”，运行中的会话标记“本轮结束后重启”。理由：MCP 的 `tools/list` 按净室过滤，切换后工具列表变了，引擎需要重新握手才能看到。重启用的是配置变化后的同一套重启机制（04 §3.4）。
- **切到深度前确认一次**：界面弹确认卡，写明“深度模式会读取原作的代码和文件；之后在净室模式下复刻时，深度模式下产生的会话和抓取结果不会被沿用”。
- **复刻运行期间**：不允许切换（返回 `BUSY`），模式在运行开始时读一次（05 §2）。

## 7. Inbox 与卡片

- `pending(project)` 读 `Inbox::pending()`，转成 `InboxRequest`。
- `answer(project, id, answer)`：
  - 有运行中的复刻：交给 `RebuildService` 的 `answer_as`，它会同时写 inbox 和 feed（05 §10）；
  - 没有：直接用 `Inbox::answer` 写 `<id>.answer.json`；
  - `Approval { always: true }` 的“总是允许”由等待方读到答案时写进 `allowed_actions`，autocraft 不自己写。
- **新卡片通知**：inbox 是目录，等待方会轮询答案文件。autocraft 用一个后台线程，每 500 ms 扫描已加载项目的 inbox 目录，发现新的 `*.request.json` 就发 `InboxNotice { project, request }`。不使用文件系统监视，因为它在 Windows 上对网络盘和杀毒软件拦截不可靠。复刻运行中，卡片由运行自己的 `relay_inbox` 发出（05 §10），扫描线程跳过正在复刻的项目，避免重复。
- **卡片超时**：执行确认和提问的等待上限都是 30 分钟。到期后等待方自己撤回请求文件，扫描线程看到文件消失就发 `InboxWithdrawn`，界面移除卡片。

## 8. 工具调用（`call`）与错误转换

```rust
fn call(&self, project: &ProjectId, call: ToolCall, cancel: &CancelFlag) -> Result<ToolReply> {
    let engine = self.engine(project)?;
    let token = ca_engine::CancelToken::default();
    let _bridge = cancel.bridge_to(&token);   // CancelFlag 置位时取消 token
    let progress = |p: Progress| self.progress_tx.try_send((project.clone(), call.tool.clone(), p.message, p.fraction));
    let consent = if call.consented { Consent::Granted } else { Consent::NotAsked };
    let opts = CallOptions::new(Caller::Ui).with_consent(consent).with_cancel(token).with_progress(&progress);
    match engine.call(&call.tool, call.params, opts) {
        Err(e) if e.code == ErrorCode::ConsentRequired && !call.consented => self.ask_consent_then_retry(...),
        r => r.map(to_reply).map_err(to_error),
    }
}
```

- 界面按钮触发的调用（列表栏、页签、命令面板执行）一律 `consented = true`：用户点按钮本身就是同意。
- 由复刻编排发起的检查用 `Caller::Ui` 加 `consented = true`。
- 进度：Engine 的进度回调转成 `AnalysisProgress` 事件，供状态行和任务页显示；同一个工具 100 ms 内最多发一次。

**错误映射**（craft-anything `ErrorCode` → autocraft code）：

| craft-anything | autocraft | 备注 |
|---|---|---|
| `BadInput`、`BadSettings`、`StaleRevision` | `INVALID`；`StaleRevision` 映射为 `CONFLICT` | |
| `NotFound` | `NOT_FOUND` | |
| `FeatureMissing` 且 `details.reason == "clean_room"` | `DEEP_REQUIRED` | 界面显示“需要深度模式”占位（06 §6） |
| `FeatureMissing`（其他）、`NotSupported` | `INVALID` | |
| `EngineMissing` | `ENGINE_MISSING` | 修复建议里是安装方法，界面附“去安装”按钮 |
| `ConsentRequired` | `CONSENT_REQUIRED` | |
| `TimedOut` | `TIMEOUT` | |
| `Cancelled` | 不作为错误：返回 `Err` 时调用方按取消处理，不显示通知 | |
| `NoPermission` | `FORBIDDEN` | |
| `FileChanged`、`FileHashMismatch`、`EvidenceHashMismatch` | `CORRUPT` | |
| `GarbledOutput`、`ProgramFailed`、`RecordingFailed` | `EXTERNAL` | |
| `OverLimit`、`Truncated` | `TOOL_FAILED` | |
| `FileError`、`CleanupFailed` | `IO`（无 `source` 时用 `EXTERNAL`） | |
| `Internal` | `TOOL_FAILED`，并记一条 `error` 日志 | |

`context` 用中文写“哪个工具失败了”，例如“伪代码生成失败”，英文原文放在 `detail` 里供“复制诊断”使用；修复建议原样保留，并标明它是英文原文。错误信息不包含工具参数和证据内容。

## 9. 分析通道服务端（`channel.rs`）

桥（03 §2）每收到一条通过令牌校验的连接，就把连接交给 `ChannelServer::serve(scope, options, reader, writer)`：

```rust
pub fn serve(&self, scope: &ChatScope, options: ChannelOptions, reader: impl BufRead, writer: Box<dyn Write + Send>) -> io::Result<()> {
    let engine = self.engine(&scope.project)?;
    let opts = ca_mcp::ServerOptions {
        all_tools: options.all_tools,
        allow_run: false,   // 执行确认一律走 inbox 卡片（§8）
        restricted: false,
        max_response_bytes: ca_mcp::DEFAULT_MAX_RESPONSE_BYTES,
        budget_for_client: false,
        ..Default::default()
    };
    let writer = ObservingWriter::new(writer, self.observer(scope));  // 见下
    let reader = PolicyReader::new(reader, scope, options, self.long_tools.clone()); // DSH 长工具、只读会话过滤，见 03 §5、05 §8
    ca_mcp::serve(engine, opts, reader, Box::new(writer))
}
```

- **每条连接一个 `ca_mcp::serve`**，它自己维护本连接的 toolset 启用状态、进行中的调用、取消。连接断开（引擎退出）时 `serve` 返回，进行中的调用会被等待结束。
- **`ObservingWriter`**：包住写出方向，看到 `tools/call` 的响应就发 `AnalysisChanged`，看到 `notifications/progress` 就转成 `AnalysisProgress`。它不修改字节，只观察。MCP 每条消息用一次 `write_all` 加 `flush` 写出一整行，但 `write_all` 可能分几次调用 `write`，所以观察者按 `\n` 切行后再解析。
- **共享写出**：`ObservingWriter` 内部是 `Arc<Mutex<管道写端>>`，一次只写一整行。`PolicyReader` 需要自己回复请求时，拿同一把锁写一整行，保证宿主插入的回复不会和 MCP 的输出交错。
- **`PolicyReader`**：包住读入方向，按行读取，处理三件事：
  1. 只读会话（`ChatPurpose::Question`）时，`tools/call` 调用带 `WRITES_FILESYSTEM`、`LAUNCHES_PROCESS`、`EXECUTES_FOREIGN_CODE`、`MUTATES_DEVICE`、`MUTATES_TARGET` 的工具，直接在宿主这边回一个 `isError` 结果，不进 Engine；
  2. DSH 长工具改写成异步（03 §5）；
  3. 宿主执行表里的工具（§10）不交给 MCP，由宿主执行并回复。

  对 `tools/list` 不做改写，所以只读会话看到的工具列表和普通会话一样，调用被拒时结果里会写明原因。
- **响应预算**：三个引擎都用默认的 `DEFAULT_MAX_RESPONSE_BYTES`，超出时返回 `over_limit`，让 Agent 按 `evidence://` 分页读取。
- **INSTRUCTIONS**：MCP 的 `initialize` 返回的使用说明原样转发，不改写工具描述。

## 10. 等待类工具在锁外执行

**问题**：`Engine::call` 在工具运行的整个过程中都持有 session 锁。同一个项目的所有调用共用一个 Engine（§2），下面几个会等待的工具如果在锁里执行就会出事：

| 工具 | 在锁里做什么 | 后果 |
|---|---|---|
| `rebuild_check` | 等复刻运行回答自查，最多 60 分钟 | 运行回答自查要调用检查工具，也要这把锁：**死锁** |
| `core_person_ask` | 等用户回答，最多 30 分钟 | 这段时间里这个项目的所有其他调用（界面、别的聊天、复刻检查）都被挡住 |
| `core_action_approve` | 结果为“询问”时等用户回答，最多 30 分钟 | 同上；pi 构建方的每个写文件、执行命令动作都经过它（03 §6.1） |
| `rebuild_question_ask` | 等只读会话回答，最多 10 分钟 | 同上 |

**做法**：autocraft-analysis 维护一张**宿主执行表**，表里的工具不进 `Engine::call`，由宿主在锁外执行。两个入口都查这张表：`AnalysisService::call`（界面、命令面板）和 `PolicyReader`（分析通道）。

| 工具 | 宿主执行 |
|---|---|
| `core_person_ask` | 解析参数（问题 1–2000 字，最多 6 个选项、每个 120 字）；`settings.questions_in(manifest) == Decide` 时立即返回 `{"answered": false, "note": <DECIDE_ANSWER 原文>}`；否则 `Inbox::post(Question, …)` 并 `Inbox::wait(id, 30 分钟, cancel)`，返回 `{"answered", "answer", "choice", "text"}` 或“没有回答”的说明。输出与 craft-anything 的 `core_person_ask` 逐字一致 |
| `core_action_approve` | 解析 `{tool_name, input, tool_use_id?}`，调用 `approve_with(inbox, auto_mode, clean_room, tool_name, input, cancel, waiting)`，返回 `{"behavior":"allow","updatedInput":input}` 或 `{"behavior":"deny","message":…}`；判定失败时回 `deny` 并写明“The approval check failed: …” |
| `rebuild_check` | `RebuildService` 的自查接口（05 §10.3） |
| `rebuild_question_ask` | `RebuildService::ask` |

- `auto_mode`、`clean_room`、`questions` 设置只在开始时用 `try_session` 短暂读一次（拿不到锁就用 `AnalysisView` 缓存里记下的值，这些值只在设置变更时改变），不在等待期间持锁。
- **响应格式**（`wire.rs`）与 MCP 完全一致：一般工具是 `{"content":[{"type":"text","text":<to_json 的 JSON>}],"structuredContent":<同一 JSON>,"isError":false}`，`to_json` 对值类结果包成 `{"result": v}`；`core_action_approve` 是协议消息，只有一个文本块、内容是裸 JSON、没有 `structuredContent`。错误用 `tool_error_body` 的格式。
- **进度与取消**：宿主执行期间发 `notifications/progress`（同一调用 100 ms 内最多一次，结束补一条），收到 `notifications/cancelled` 时置位取消。
- **Engine 里的注册**：这几个 id 仍然注册在 Engine 里（`core_*` 是 craft-anything 自带的，`rebuild_*` 由 autocraft-rebuild 提供，05 §11），这样 `tools/list`、参数 schema、净室白名单都保持不变。万一有调用绕过宿主执行表进入 Engine：`rebuild_check`、`rebuild_question_ask` 的 ToolFn 对进程内调用者返回 `FeatureMissing`（“构建过程中不能在同一进程里自查”），`core_*` 走原实现（只是会持锁等待）。
- **长时间运行但不等人的工具**（Ghidra、网页抓取、Frida、素材生成）照常在锁里执行，同一项目的其他调用排队等待；界面用 `try_session` 读视图，不会卡住（§5）。
- **执行确认**：MCP 的 `ask_consent` 在 `engine.call` 返回 `ConsentRequired` 之后才等待（锁已经释放），不需要宿主执行。`AnalysisService::call` 遇到同样的错误时也在锁外投卡等待，再带 `Consent::Granted` 重试（§8）。
