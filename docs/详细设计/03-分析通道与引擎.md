# 03 分析通道与引擎（`autocraft-bridge`、`autocraft-agents`）

## 1. 一个聊天的启动顺序

1. `router.prepare(RouteRequest { chat, project, backend, new_session, model, effort })`。`model` / `effort` 取项目级选择（04 §3）。
2. `router.signature(..)`，用于之后判断要不要重启。
3. `support_dir(chat)`：`<data>/engines/support/<chat>/`。
4. `analysis.open(project)` 并 `hold(project, Chat(chat))`（02-分析服务 §2）。
5. `bridge.register(ChatScope { project, chat, purpose }, ChannelOptions)`，得到令牌，组成 `AnalysisAccess`。
6. 构建方会话（`purpose == Builder`）另外带上 `BuilderHooks`（§6）。
7. 组装 `StartSession`，调用 `runtimes[backend].start(req, sink)`。
8. 新会话拿到 `NativeSessionKey` 后写 `chat_bindings`。

任何一步失败都反向清理：`router.release`、删除 support 目录、`bridge.revoke`，再 `analysis.release(project, Chat(chat))`。聊天关闭和引擎退出时也执行同样的释放。

`cwd`：分析聊天用项目根目录；构建方用 `Workspace::app_dir()`；“只是问问”用项目根目录。

## 2. 管道与 `mcp-host`

### 2.1 为什么是字节流

craft-anything 的 MCP 服务器会主动发消息（`notifications/progress`、`notifications/tools/list_changed`），所以管道是**透明的双向字节流**，`mcp-host` 不解析 MCP。

### 2.2 协议

- **管道名**：`autocraft-<uuid v4 simple>`，用 `interprocess` 的 `GenericNamespaced` 本地 socket（Windows 上是命名管道）。
- **连接**：
  1. 客户端（`mcp-host`）连上后写一行 `<token>\n`；
  2. 服务端在 64 KiB 内读到换行，查令牌表，找不到就关闭连接；
  3. 之后两个方向都是 MCP 的换行分隔 JSON-RPC，原样透传，服务端交给 `ChannelServer::serve`（02-分析服务 §9）。
- **令牌**：两个 UUID v4 拼接（64 个十六进制字符）。每次引擎启动签发一个，`revoke` 后已有连接在下一次读入时断开。
- **连接上限**：64 条。超过时直接关闭新连接并记 `warn`。
- **单行上限**：craft-anything MCP 的 64 MiB 请求上限；响应大小由它的响应预算控制。

### 2.3 `autocraft.exe mcp-host`

```text
autocraft.exe mcp-host
  读环境变量 AUTOCRAFT_PIPE、AUTOCRAFT_TOKEN（缺一个就向 stderr 写一行原因并以退出码 2 退出）
  连接管道，发送令牌
  两个线程：stdin → 管道，管道 → stdout，按块复制，不解析
  任一方向 EOF 或出错：关闭另一方向，退出码 0
```

- stdout 只承载协议字节，不写日志；日志写到 `<data>/logs/`，用同一套 observability 初始化，但不打开 UI。
- `mcp-host` 不读 `autocraft.db`，也不加载 craft-anything。

### 2.4 `autocraft-bridge` 接口

```rust
pub struct Bridge { /* pipe, tokens */ }

impl Bridge {
    pub fn start(server: Arc<dyn ChannelHandler>) -> Result<Self>;
    pub fn pipe_name(&self) -> &str;
    pub fn register(&self, scope: ChatScope, options: ChannelOptions) -> String;
    pub fn revoke(&self, token: &str);
}

/// 由 autocraft-analysis 的 ChannelServer 实现。
pub trait ChannelHandler: Send + Sync {
    fn serve(&self, scope: &ChatScope, options: ChannelOptions,
      reader: Box<dyn BufRead + Send>, writer: Box<dyn Write + Send>) -> std::io::Result<()>;
}
```

`autocraft-bridge` 只依赖 core 和 `interprocess`，不依赖 craft-anything。每条连接一个线程，线程里调用 `handler.serve(..)`，返回时连接结束。

## 3. 三个引擎怎么注册分析通道

服务器名统一为 `autocraft`。Agent 看到的工具名前缀由各引擎自己加（如 `mcp__autocraft__<id>`），craft-anything 会自动去掉 `mcp__srv__` 前缀，所以工具 id 都能识别。

| 引擎 | 位置 | 内容 |
|---|---|---|
| pi | 扩展文件 `support_dir/pi-autocraft.js` | `pi.registerMcpServer("autocraft", { command: process.env.AUTOCRAFT_EXE, args: ["mcp-host"], exposure: "direct", timeout: 600, description: … })`。进程环境注入 `AUTOCRAFT_EXE`、`AUTOCRAFT_PIPE`、`AUTOCRAFT_TOKEN` |
| OMP | `~/.omp/agent/mcp.json` | 合并写入 `"autocraft-analysis": {"type":"stdio","command":"<exe 绝对路径>","args":["mcp-host"],"env":{"AUTOCRAFT_PIPE":"${AUTOCRAFT_PIPE}","AUTOCRAFT_TOKEN":"${AUTOCRAFT_TOKEN}"}}`，OMP 进程环境注入这两个变量。只增删 `autocraft-` 开头的键，内容不变不写。`--config` 叠加的配置里设 `tools.xdev: false`，让 OMP 直接列出 MCP 工具 |
| DSH | `session/new`、`session/resume` 的 `mcpServers` | `{"name":"autocraft","command":"<exe 绝对路径>","args":["mcp-host"],"env":[{"name":"AUTOCRAFT_PIPE","value":"…"},{"name":"AUTOCRAFT_TOKEN","value":"…"}]}`。DSH 会清空父进程环境，值必须直接写在参数里，经 stdin 传，不落盘 |

- 用户 MCP 的投影条目也用 `autocraft-` 前缀（`autocraft-<name>`）。
- 启动引擎前从继承的环境里剔除引擎、宿主和云服务商相关前缀的变量（`PI_`、`OMP_`、`DSH_`、`AUTOCRAFT_`、`AWS_` 等，见 `crates/agents/src/process.rs::is_isolated`），再注入本次的值。
- DSH 的 patch 关闭 `tool-todo`，计划统一用 `core_plan_update`。

## 4. 工具面

### 4.1 由 craft-anything 提供的部分

Agent 看到的工具、元工具、prompts、resources、执行确认、响应预算都由 craft-anything MCP 的 `serve` 提供，autocraft 不改。另外注册进 `Engine` 的只有 `rebuild_*`（05 §11）。`initialize` 返回的使用说明原样转发。

### 4.2 渐进启用

`ChannelOptions.all_tools` 按引擎取 `crates/agents/src/lib.rs` 的常量表：

```rust
pub const ALL_TOOLS: [(BackendKind, bool); 3] = [(Pi, false), (Omp, false), (Dsh, false)];
```

三个引擎都会在收到 `tools/list_changed` 后重新执行 `tools/list`，所以都用渐进启用：一开始只列 core 工具和 `list_toolsets` / `enable_toolset`。即使客户端没刷新列表，按 id 直接调用未启用的工具也能用，因为 craft-anything 在 `tools/call` 里会自动启用对应的 toolset。

## 5. DSH 长工具异步变体

DSH 的 MCP 调用固定 60 秒超时，收到 `notifications/progress` 也不会续时。`ChannelOptions.async_long_tools` 只对 DSH 为 `true`。

**哪些算长工具**（`crates/analysis/src/catalog.rs`）：按工具的 `ToolSpec` 判断，不靠名字：

- `effects` 含 `LAUNCHES_PROCESS`、`ACCESSES_NETWORK`、`EXECUTES_FOREIGN_CODE` 之一；或
- `requires` 是 `Ghidra` 或 `Engine(_)`；或
- id 在一张很短的补充表里（纯 Rust 但可能很慢的分析：`native_function_pseudocode`、`native_call_graph_show`、`js_app_map`、`core_target_triage`）。

**流程**（`PolicyReader` 截住 `tools/call`）：

1. 宿主立即回复这个 JSON-RPC 请求：`{"content":[{"type":"text","text":"Started <tool> in the background (job <n>). Its result will arrive as your next message; continue with other work or wait."}],"isError":false}`；
2. 在后台线程用同一个 Engine 执行 `Engine::call(Caller::Mcp, Consent::NotAsked)`，需要确认时同样走 inbox 卡片；
3. 完成后，把结果（与 MCP 的 `success_body` 格式相同，超出预算时同样折叠成 `over_limit`）组成一段文字：`Result of background job <n> (<tool>):\n<json>`，交给 `autocraft-agents`：
   - 会话空闲：`prompt(text)`；
   - 会话运行中：DSH 不支持插话，排到本轮结束后再 `prompt`。
4. 取消：DSH 在 60 秒内取消原请求时不影响后台任务；用户停止会话时，后台任务一起取消。

## 6. 构建方权限钩子（`BuilderHooks`）

复刻构建方会话的每个写文件、执行命令、访问网络动作都要经过项目的审批策略（05 §4）。三个引擎的接入点：

| 引擎 | 接入点 |
|---|---|
| pi | 扩展里注册 `pi.on("tool_call", handler)`，`handler` 返回 `{ block: true, reason }` 拒绝。pi 自己不对工具调用发权限请求 |
| OMP | 构建方会话以 `--approval-mode yolo` 启动，关掉 OMP 自己的审批卡；审批由投影的扩展完成：扩展里的 `tool_call` 钩子和 pi 一样用 `ctx.ui.input("autocraft:approve", …)` 交给宿主判定（§6.1）。其他会话用 `--approval-mode always-ask` |
| DSH | 构建方每次启动挂载生成的 `tools/pre-execute` 插件：非只读原生工具先请求审批，再交给 `session/request_permission` 适配器调用项目策略；MCP 工具继续由分析通道审批。ACP 权限请求只带 `toolCallId` 时，从已提交的 `tool_call` 帧按 id 关联原始工具名和 `rawInput`，不解析标题文案。放行选 `allow_once`，拒绝选 `reject_once`，缺失选项则取消 |

DSH 的项目审批放行不等于绕过原生沙箱。项目外的文件操作仍可能被 `workspace-write` 拒绝；宿主不自动改参或重放。Agent 收到明确的沙箱拒绝后，只能按工具 schema 对同一路径 / 内容显式请求一次 `sandbox_permissions` 与 `justification`；升级只影响本次调用，仍会再次经 ACP 和项目策略审批。全局及只读会话的沙箱保持不变。

### 6.1 pi：扩展与宿主之间怎么问

pi 和 OMP 的 `tool_call` 钩子在引擎进程里运行，拿不到 `executeTool`，不能直接调用 MCP 工具。所以钩子用 `ctx.ui.input("autocraft:approve", <动作 JSON>)` 把动作交给宿主；适配器在构建方会话里拦下这个对话框（`crates/agents/src/approvals.rs`），调用 `BuilderHooks.policy.decide`，回 `{allow, reason}`。

### 6.2 OMP、DSH：适配器内判定

- `StartSession.builder` 为 `Some` 时，适配器收到权限请求后：
  1. 把请求翻译成 `AgentAction`（§6.3）；
  2. 在独立线程调用 `policy.decide(&action, &cancel)`（可能等用户回答最多 30 分钟）；
  3. 按结果回复引擎。
- `ActionPolicy` 由 `autocraft-rebuild` 实现（05 §4），内部调用 craft-anything 的 `approve_with`。
- 构建方会话停止时，`cancel` 置位，等待中的判定返回 `Refuse`，适配器回复取消。

### 6.3 动作翻译

统一翻译成 craft-anything `decide()` 认识的工具名和参数：

| 来源 | 条件 | 翻译为 |
|---|---|---|
| pi / OMP 工具调用 | `write` | `Write {file_path: input.path}` |
| | `edit` | `Edit {file_path: input.path}` |
| | `bash` | `Bash {command: input.command}` |
| | `powershell` | `PowerShell {command: input.command}` |
| | `read`、`grep`、`find`、`ls` | 不判定，直接放行 |
| | `mcp__autocraft__*` 或名字是分析工具 id | 不判定（MCP 自己处理执行确认） |
| | 其他 | `Other {tool, input}`，按 `OtherTools` 类别处理 |
| DSH `request_permission.toolCall` | `kind` 为 `edit`/`delete`/`move` | `Write {file_path: locations[0].path ‖ rawInput.path ‖ rawInput.file_path ‖ rawInput.abs_path}` |
| | `execute` | `Bash {command: rawInput.command}`（数组用空格连接） |
| | `read`/`search` | 放行 |
| | `fetch` | `WebFetch {rawInput}` |
| | `think`/`switch_mode` | 放行 |
| | 其他 | `Other {tool: title}` |

翻译表放在 `autocraft-agents` 里每个引擎自己的模块，`AgentAction` 到 `(tool_name, input)` 的转换放在 `autocraft-rebuild::approvals`。

## 7. 运行中插话（`steer`）

复刻构建过程中用户补充的说明，要在构建方的下一步就送到，而不是等整轮结束（05 §7）。

| 引擎 | 实现 | `Capabilities.steer` |
|---|---|---|
| pi | RPC 命令 `{"type":"steer","message":…}` | `true` |
| OMP | RPC `steer`，下一次模型请求就能看到 | `true` |
| DSH | ACP 没有插话，退回本轮结束后发送 | `false` |

## 8. 技能与系统提示

- `crates/agents/skills/` 下是 autocraft 自己的技能，英文：

  | 技能 | 用途 |
  |---|---|
  | `investigating-a-target` | 分析聊天的方法：先 `core_session_show` / `core_targets_list` / `core_investigation_show`，先看摘要再分页，证据 id 必引，事实和推断分开，不确定的写 `core_unknown_add`，每轮结束 `core_handoff_write` |
  | `rebuilding-from-evidence` | 构建方：从 `capture/` 和证据出发，`rebuild_check` 自查，遵守净室规则 |

- 一条 `ANALYSIS_RULE`（`crates/agents/src/workflow.rs`）：一句话说明分析工具在哪个 MCP 服务器下、证据 id 如何引用。
- 注入方式：pi `--skill` + `systemPromptOptions.sections`；OMP `skills.customDirectories` + 扩展；DSH patch 的 `personaPrefix` / `customSkillDirs`。
- 只读会话（“只是问问”）不加载技能，系统提示用 `crates/rebuild/src/question.rs` 的 `PREAMBLE`。

## 9. 只读会话（`SessionRole::ReadOnly`）

用于“只是问问”（05 §8），按引擎关闭写入类内置工具：

| 引擎 | 做法 |
|---|---|
| pi | `--no-session --no-skills --tools read,grep,find,ls` |
| OMP | `--no-skills --tools read`；适配器对写入、执行类请求一律回拒绝 |
| DSH | patch：`tool-fs` 的 `write: false`、`edit: false`，并关闭其他写入类工具 |

分析通道照样连接，但 `PolicyReader` 拒绝有副作用的分析工具（02-分析服务 §9）。净室模式下只读会话不读项目文件以外的东西。
